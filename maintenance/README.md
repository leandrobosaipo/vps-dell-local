# Temporary JP inbound collector

This is a private, receive-only holding point for JP events during a controlled migration. Its explicit `--source evolution` mode accepts the Evolution webhook directly before the n8n queue. The default `--source n8n` mode preserves the previous n8n contract. It never forwards to Central, interprets an event, sends WhatsApp, or replays a record. It has only `POST /inbound` and `GET /healthz`.

Rust was evaluated for this bounded component. Node 22 is already cached for the target and these tools use native Node crypto and filesystem operations. This keeps the temporary runtime and deployment smaller, without adding a new toolchain or dependency. No production deployment is part of this source change.

## Local contract

Direct Evolution mode: `node maintenance/ingress.mjs --source evolution --dir PATH --bind 127.0.0.1 --port 8787 --token-file PATH --key-file PATH --instance-file PATH [--min-free-bytes N]`. It rejects `--workflow-id`. Default n8n mode uses the same arguments plus `--workflow-id ID` and may explicitly set `--source n8n`. All three secret file paths are CLI arguments; their **values** must never be put in argv, logs, or source. The token and instance files contain UTF-8 text, optionally ending in a newline. The AES-256-GCM key file contains exactly 32 raw bytes. Files must be regular, owned by the process UID, mode `0600`, and have one link. The storage directory is created mode `0700` if absent and must be owned by the process UID; the final directory cannot be a symlink. `--min-free-bytes` is an optional conservative free-space floor; allow at least that many bytes plus twice the body size on the filesystem. Bind and route it only on the private approved path.

The only accepted write request is `POST /inbound` with `Authorization: Bearer <configured token>` and JSON `instance` equal to the configured instance. A top-level array is accepted only if every element has that instance. Direct Evolution mode needs no n8n headers and rejects them if presented. It retains the exact bytes of the Evolution HTTP body received by this collector, including formatting and unknown event types. The default n8n mode also requires `X-JP-N8N-Workflow-Id: <exact configured inbound workflow ID>` and `X-JP-N8N-Execution-Id: <decimal n8n execution ID>`. It retains the HTTP body received from n8n; the current workflow forwards parsed `$json.body`, so these bytes need not match the original Evolution HTTP bytes. The maximum body is 16 MiB; oversize returns `413`. Authentication and instance failures return `401`; malformed JSON returns `400`; persistence or integrity failure returns `503`. Only an fsynced record returns `202 {id, duplicate}`. `GET /healthz` returns a status and record count only. There is no control, dump, resume, shell, or replay endpoint.

Each record is named by SHA-256 of the length-prefixed instance and received HTTP body bytes. Exact retries within one source return the same ID and retain the first provenance. A byte-identical body arriving from the other source is a provenance conflict and returns `503` for manual reconciliation. A different update to the same message ID has different bytes and becomes a distinct record. New metadata includes `source`: direct Evolution records have `workflowId: null` and `executionId: null`; n8n records retain those validated values. The file also contains version, received time, raw SHA-256, instance, IV, AES-256-GCM ciphertext, and authentication tag. Metadata is authenticated as GCM AAD. File creation uses an exclusive mode-0600 temporary file, complete write, file fsync, exclusive hard link, temporary unlink, and directory fsync before `202`. A retry can verify and recover a linked file after an interrupted attempt. Any unreadable, tampered, or ambiguous record blocks acknowledgement. Do not manually edit or remove records.

`readRecord(file, key, expectedInstance)` is an offline decoder for later audited reconciliation. It verifies file ownership/mode, source-specific provenance, GCM, raw hash, instance, and filename before returning the received body `Buffer`. Existing version-1 records without `source` decode as n8n; the decoder does not alter their authenticated stored metadata. It does not replay or parse business meaning. Keep the key and storage in private restricted locations; the metadata remains visible to someone with filesystem read access. Collecting an event is evidence of durable intake only, not Central processing, scheduling, WhatsApp delivery, or consumer receipt.

Run fictional local tests with `node --test maintenance/test_ingress.mjs`. The tests use loopback HTTP, temporary keys and data, and a child process crash. No production endpoint or credential is contacted.

## Bounded maintenance profile

`container.json` pins the already observed Mac API image only to reuse its Node 22 runtime, overrides its entrypoint, and does not run the application or mount its state/configuration. The receive-only container has no published port, a read-only root, dropped capabilities, bounded memory/CPU/PIDs and no log driver. The isolated host directory contains source, a private credential/key directory and encrypted records. It must be created exclusively, source hashes verified, credential files root 0600, storage root 0700. The existing webhook Bearer is delivered privately; never put it in Docker environment, labels, command arguments or source.

This is a temporary intake repair on the existing Mac host, not the migration to Dell. Changing the single JP webhook URL requires an exact private before-copy, confirmation that all other fields are unchanged, and readback. Old emit/retry operations may retain their prior URL; keep that endpoint and its data available. No cancellation/deletion of the shared n8n queue, replay or implicit clock/emitter restart is part of this profile.

`read-api-counters.mjs` is a one-shot diagnostic function intended to be evaluated by an administrative Node child in the existing JP API container. It temporarily opens only the local, unpublished Node Inspector, reads the known request callback's existing numeric/boolean counters and `isBusy()` functions, then closes it. It does not patch a listener, assign variables, set a breakpoint, execute a business route, stop a queue or return scope secrets. Check Inspector closure independently after use. It excludes inbound and does not prove that a request already handed to Evolution ended. An idle snapshot requires the admission fence and provider-side evidence before a restart.

`fence-api.mjs` is a separate **mutating** maintenance operation: it calls the existing identified HTTP server's native `close()` once, then observes the completion callback, zero connections and idle module counters, retaining the server/scope references while in-flight requests finish. It never patches a listener or changes application flags. Before invoking it, stop the dedicated proxy, confirm `RestartPolicy=no` on the exact API container, and verify both intake paths. A drained result is only the local API boundary; externally verify listener and Inspector closure, stop/read back the same container, and preserve the last send attempt. It is not a provider queue proof or authorization to restart any WhatsApp session. `canRestart` always stays false. If the bounded observation fails, the listener can remain closed: keep intake, snapshots and the output hold, inspect the exact state, and do not blindly invoke it again or restart the API.

The bounded Node 22 fixture holds a real HTTP request until the test observes new connections refused, then releases it and requires the real counter to reach zero. Re-read the handler's `[[Scopes]]` chain on each sample: a previously materialized Module scope can retain old primitive values. Native `close()` completion is observed through the remote Promise state without awaiting it in a blocking CDP command. The existing Inspector guard must leave an already open inspector and listener untouched.
