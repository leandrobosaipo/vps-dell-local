# Temporary JP inbound collector

This is a private, receive-only holding point for JP events sent by n8n during a controlled migration. It never forwards to Central, interprets an event, sends WhatsApp, or replays a record. It has only `POST /inbound` and `GET /healthz`.

Rust was evaluated for this bounded component. Node 22 is already cached for the target and these tools use native Node crypto and filesystem operations. This keeps the temporary runtime and deployment smaller, without adding a new toolchain or dependency. No production deployment is part of this source change.

## Local contract

Start with `node maintenance/ingress.mjs --dir PATH --bind 127.0.0.1 --port 8787 --token-file PATH --key-file PATH --instance-file PATH --workflow-id ID [--min-free-bytes N]`. All three secret file paths are CLI arguments; their **values** must never be put in argv, logs, or source. The token and instance files contain UTF-8 text, optionally ending in a newline. The AES-256-GCM key file contains exactly 32 raw bytes. Files must be regular, owned by the process UID, mode `0600`, and have one link. The storage directory is created mode `0700` if absent and must be owned by the process UID; the final directory cannot be a symlink. `--min-free-bytes` is an optional conservative free-space floor; allow at least that many bytes plus twice the body size on the filesystem.

The only accepted request is `POST /inbound` with `Authorization: Bearer <configured token>`, `X-JP-N8N-Workflow-Id: <exact configured inbound workflow ID>`, and `X-JP-N8N-Execution-Id: <decimal n8n execution ID>`. The payload must be JSON with `instance` equal to the configured instance. A top-level array is accepted only if every element has that instance. The collector retains the exact bytes of the **HTTP body it receives from n8n**, including formatting and unknown event types. The current n8n workflow forwards parsed `$json.body`, so these bytes are not guaranteed to match the original Evolution HTTP bytes. The maximum body is 16 MiB; oversize returns `413`. Authentication and instance failures return `401`; malformed JSON returns `400`; persistence or integrity failure returns `503`. Only an fsynced record returns `202 {id, duplicate}`. `GET /healthz` returns a status and record count only. There is no control, dump, resume, shell, or replay endpoint.

Each record is named by SHA-256 of the length-prefixed instance and received n8n HTTP body bytes. Exact retries return the same ID and retain the first workflow/execution provenance. A different update to the same message ID has different bytes and becomes a distinct record. The file contains version, received time, raw SHA-256, instance, workflow/execution provenance, IV, AES-256-GCM ciphertext, and authentication tag. Metadata is authenticated as GCM AAD. File creation uses an exclusive mode-0600 temporary file, complete write, file fsync, exclusive hard link, temporary unlink, and directory fsync before `202`. A retry can verify and recover a linked file after an interrupted attempt. Any unreadable, tampered, or ambiguous record blocks acknowledgement. Do not manually edit or remove records.

`readRecord(file, key, expectedInstance)` is an offline decoder for later audited reconciliation. It verifies file ownership/mode, GCM, raw hash, instance, and filename before returning the original `Buffer`. It does not replay or parse business meaning. Keep the key and storage in private restricted locations; the metadata remains visible to someone with filesystem read access. Collecting an event is evidence of durable intake only, not Central processing, scheduling, WhatsApp delivery, or consumer receipt.

Run fictional local tests with `node --test maintenance/test_ingress.mjs`. The tests use loopback HTTP, temporary keys and data, and a child process crash. No production endpoint or credential is contacted.
